Twin governance: versions, owners, who may act on it

A twin that nobody can audit is a rumour with a dashboard. Tonight you give Kittiwake Hall's thermal twin the three things that make it accountable: a version stamp on every prediction, a named owner on every link of the loop (including the one who owns the surprises), and gates a model version must pass before it may advise or act. Kittiwake Hall is a constructed six-storey teaching building; every number about it is generated by the bench engine, and the decision log you audit live is constructed too.

Part 0

Kittiwake's twin, with someone accountable

By practitioner session 7 Kittiwake's twin (constructed) tracks every floor to 0.218 C, plans the setback week within 1.7 percent on energy, and puts a band around its what-if runs that covers 96.8 percent. It is good enough that people will start acting on it. That is exactly the moment it needs governance: the day its advice changes the building, a wrong model version stops being a modelling bug and becomes a decision someone has to answer for.

LiveWhy governance is part of the twin, not paperwork around it3 min▶

A simulation answers a question once. A twin keeps answering, from a model that is refitted, about an asset that is changed, on data that arrives with gaps. Three things move at once, so every answer needs to say which version of each it came from. And because the answers feed decisions that change the building, someone has to own each part of the loop and someone has to decide which model version is trusted to do what.

Real world

The AIAA and AIA (2020) position paper defines a twin as dynamically updated with data from its physical twin throughout its life cycle and as informing decisions that realize value. Its life-cycle phases, As Designed, As Built, As Used and As Maintained, are versions of the asset by another name. Governance is how you keep the twin's versions pointing at the right ones.

Self-studyWords for the governance side3 min▶
  • Configuration version. The asset as it physically is; it increments on every logged physical change (practitioner session 6).
  • Model version. Structure, parameter values and where each came from, plus the configuration it was fitted to.
  • Data version. Which feeds, over which window, with which gap-filling rule.
  • Model card. One record a reviewer can read in two minutes: what the model is, what it was checked against, what it gets wrong, who owns it, what it may do.
  • Promotion. Moving a model version up a tier (shadow, advise, act with approval). Demotion is the same move downward and must be just as easy.
  • The surprises. The innovations: reading minus prediction. Practitioner session 5 watches them for drift; tonight someone owns them.
Part 1 · covers the three version ids and the decision trail

Every prediction carries three versions

7 min live

A prediction from a twin is only auditable if it says which building, which model and which data produced it. Drop any one and the question "was this advice wrong, and why?" has no answer. The figure stamps all three on one prediction and draws the decision log row from practitioner session 1 pointing back at it.

LiveThe three ids, and what each must answer4 min▶

Asset configuration version. Which physical building the prediction is about. Floor 4 in config 3 and floor 4 after an insulation retrofit are different assets for a thermal model, even though the floor id is the same.

Model version. The structure (two thermal nodes per floor), every parameter value with where it came from, and the configuration it was fitted to. In Kittiwake's calibration, kU for floor 4 came out 1.42 against 1.41 true, but kC came out 0.90 against 0.88 only by luck: other floors were far off (floor 3: 1.68 found against 0.89 true). The model version must carry that "weakly identified" note, or a reviewer will trust a number the data never pinned down.

Data version. Which feeds, over which window, and how gaps were handled. Two runs of the same model on the same week give different predictions if one filled a missing hour silently. How to run feeds well lives in learn IoT data; tonight the only rule is that the rule itself gets a version.

LiveThe decision log closes the trail3 min▶

The decision log row from practitioner session 1 carries the prediction it relied on and that prediction's model version. With the three stamps, the trail runs all the way back: decision, prediction, model, the configuration the model was fitted to, the data it saw. When a model version is found wrong, the log tells you which decisions to revisit. Without it, all you can say is "the twin was wrong for a while".

Real world

The AIAA and AIA (2020) paper says plainly that having a twin requires a physical asset, and its As Maintained phase is the asset after people have changed it. A model version that points at As Built while the asset has moved to As Maintained is the most common way a twin goes quietly wrong.

Self-studyVersions in a warehouse versus versions in a twin3 min▶

A warehouse versions its code and maybe its schema; the rows describe events that happened and do not change. A twin's rows are predictions about an asset that does change, from a model that is refitted. So a twin needs one more join than a warehouse ever did: from every prediction to the physical configuration it assumed. Treat fitted_to as a foreign key, and a mismatch with the asset's current configuration as a failed constraint.

Part 2 · covers owners for each link and the audit of a decision log

An owner for every link, including the surprises

6 min live

The twin loop from leader session 1 has four links: the asset, the data link, the model, the decision. Each needs an owner who can be asked a question and give an answer. And there is a fifth job nobody draws: watching whether the loop still holds. The figure puts an owner on each link and the check in the middle, in copper, because it is the one that is usually left to "everyone".

LiveReading the audit3 min▶

The check is a join. For each decision, compare the model's fitted_to with the asset's configuration on the decision date. With the retrofit logged, three of the six constructed decisions relied on a model fitted to a configuration the floor was no longer in.

The cost is not hypothetical. For floor 4 the engine runs the same model version on the retrofitted floor: its week-2 energy estimate is +63.1 percent off. On the floor it was fitted to, the same model is -1.3 percent off. Same model, same code, same owner; the only difference is a physical change the model never saw.

Now switch the retrofit to "never logged". The audit finds only one stale row, because the asset record still says config 3. The cost on floor 4 is unchanged. A version check is only as good as the change log it joins against, which is practitioner session 6's argument, and why the surprises need an owner of their own.

LiveThe owner nobody names: the surprises3 min▶

The asset owner logs changes they know about. The modeller refits on a schedule. The budget holder acts on advice. None of them is paid to notice that floor 4's innovations moved from +0.015 C on average in week 1 to +0.638 C in week 2 (z 11.44, constructed). That job, reading the surprises and the band coverage every week and having the authority to demote a model version, needs one named owner. When it belongs to everyone, the unlogged retrofit is caught by nobody.

Real world

The National Academies (2024) report calls verification, validation and uncertainty quantification an area of particular need for twins, and concludes that it must be a continual process that adapts to changes in the physical counterpart. A one-off validation at launch does not meet that bar; an owned weekly check of the surprises is the smallest thing that does.

Self-studyWhere the standards stop2 min▶

ISO 23247-1:2021 sets out a digital twin framework for manufacturing and, from its published contents, frames the twin around observable manufacturing elements (reported: the standard is paywalled and its clauses were not read here, so no requirement is quoted). Whatever a framework prescribes, an observable element still needs someone accountable for the observation and someone for the model of it. Neither the National Academies (2024) report nor the AIAA and AIA (2020) paper assigns those roles for you.

Self-studyWhat is out of scope here1 min▶

Who is legally liable when a twin's advice goes wrong depends on contracts and jurisdiction; nothing here is legal or compliance advice. The energy figures are a constructed building's heating, not money advice: nothing here is investment advice. Detectors for the surprises live in learn anomaly detection.

Part 3 · covers tiers of action and promotion gates

Who may act on it, and when

7 min live

A model version does not get to act because it is new or because its tracking looks good. It climbs tiers, and each climb has a gate with a number on it. The figure is the ladder Kittiwake's twin would use; the copper gate is the one that matters most and is skipped most often: the band held.

LiveThree tiers of action3 min▶

Read-only advice. The twin's what-if runs appear in front of people with their bands; nothing changes in the building because the twin said so. Most twins should live here for a long time.

A person approves. The twin proposes a schedule; a named owner signs it before it is applied, and the decision log records who signed and which model version proposed it.

Automatic within limits. The twin writes setpoints itself, inside hard limits, with an override and a rollback. That tier, and what being wrong costs in a real building, is practitioner session 9. When twins that act without people become normal is contested, and no date is given here.

LiveThe gates, with Kittiwake's numbers3 min▶

To advise: a check week. The model is calibrated on week 1 and checked on week 2, a week it never saw. Kittiwake's calibrated twin with the filter tracks the true room to 0.218 C and estimates setback-week energy within +1.7 percent (constructed). A model checked only on the week it was fitted to has proved nothing.

To act: the band held. Coverage of the what-if band must sit near its nominal 95 percent: the bench uses 90 to 99.5 percent as its own self-check range. The honest twin covers 96.8 percent. The same twin told to trust its sensors fully covers 77.4 percent: its band is too narrow and it would act with confidence it has not earned. And the innovations must be un-flagged: with the unlogged retrofit, floor 4's innovation shift is z 11.44.

Gate each floor, not the building. With the retrofit, the building's coverage is 92.1 percent, inside the range, while floor 4's is 69.0 percent. A building-level gate would have promoted the very model that is 63.1 percent off on floor 4. The overall tracking error, 0.258 C, still looks fine: the filter follows the sensors, and only the surprises carry the warning.

Self-studyDemotion has to be as easy as promotion2 min▶

Every gate also runs backwards. When the owner of the surprises sees a floor flagged, that floor's model version drops to read-only advice until it is refitted on the new configuration and passes a fresh check week. If demotion needs a meeting, it will not happen in time. Write it as a rule the check applies on its own, and log every move up or down in the same decision log.

Real world

The National Academies (2024) report puts it in one line: "A digital twin is more than just simulation and modeling." The part that is more, the loop back into the physical world, is exactly the part that needs rules for who may close it.

Build-along

Write Kittiwake's model card and a check that refuses

★ 22 min · everyone builds

You will write one model card for Kittiwake's twin, then a short Python check that reads a card and the asset record and refuses the model version if it was fitted to a different configuration or if its band coverage is outside 90 to 99.5 percent. The figure is the card and the two fields the check reads.

Write the model card

One card per model version, in plain YAML a reviewer can read in two minutes. Every parameter says where it came from; the check results say which week they were measured on; the weakness is written down, not left for someone to discover. Copy and adapt.

model_card.yamlmodel_version: KH-twin-v2 structure: 2-node RC per floor (room air, building mass) fitted_to: {config_version: 3 per floor, data: week 1} data: {feeds: [weather, sun, heat meters, room sensors, timetable], window: week 1, hourly, gap_rule: flag, never fill silently} params: Ci: {value: 6.0, unit: kWh/K, from: drawings} kU: {values: [1.50, 1.20, 1.26, 1.42, 1.42, 1.28], from: calibration week 1} kC: {values: [1.62, 1.00, 1.68, 0.90, 0.80, 1.20], from: calibration week 1, note: weakly identified} sensor_sd: {value: 0.4, unit: C, from: assumed} checks_week_2: tracking_rmse_c: 0.218 energy_error_pct: +1.7 band_coverage_pct: 96.8 # nominal 95 known_weakness: kC (one week pins down heat loss, not thermal mass) owner: the modeller surprises_owner: (one named person) allowed_actions: [advise_read_only, person_approves]

Write the asset record it must match

The card is checked against the asset, not against itself. After floor 4's retrofit is logged, the asset record moves to config 4.

asset_f4.yamlfloor_id: KH-F4 config_version: 4 change_log: - version: 4 date: start of week 2 change: insulation retrofit logged_by: (who)

Write the check that refuses

Twelve lines. It refuses a card fitted to a different configuration, or one whose band coverage falls outside 90 to 99.5 percent. The two toy cards reuse Kittiwake's honest coverage (96.8) and the trust-the-sensors coverage (77.4). Save it as gate.py in a scratch folder and run python3 -I gate.py.

gate.pydef check(card, asset): why = [] if card["fitted_to"] != asset["config_version"]: why.append(f"fitted to config {card['fitted_to']}, asset is config {asset['config_version']}") if not 90.0 <= card["coverage_pct"] <= 99.5: why.append(f"coverage {card['coverage_pct']} outside 90 to 99.5") return "REFUSE: " + "; ".join(why) if why else "ACCEPT" asset = {"floor_id": "KH-F4", "config_version": 4} cards = [{"version": "F4-v3", "fitted_to": 4, "coverage_pct": 96.8}, {"version": "F4-v2", "fitted_to": 3, "coverage_pct": 77.4}] for c in cards: print(c["version"], check(c, asset))
OutputF4-v3 ACCEPT F4-v2 REFUSE: fitted to config 3, asset is config 4; coverage 77.4 outside 90 to 99.5

Make it fail the right way

Set the asset back to config 3 and run again: F4-v2 should now be refused for its coverage alone, and F4-v3 for its configuration. Then change 99.5 to 100 and ask yourself why an upper limit exists at all: a band that covers everything is too wide to plan with.

try nextasset = {"floor_id": "KH-F4", "config_version": 3} # run it and read the output: which card is refused, and for which reason?

Gate per floor

Extend the card with one coverage value per floor and make the check refuse if any single floor falls outside the range. With Kittiwake's retrofit, the building passes at 92.1 percent while floor 4 sits at 69.0 percent (constructed): your check should refuse.

per-floor rulechecks_week_2: band_coverage_pct_by_floor: [...] # one per floor rule: refuse if any floor is outside 90 to 99.5, or any floor's innovations are flagged

The habit to keep. No model version advises without a card, and no card passes without matching the asset's current configuration and a band that held on every floor. Put the check where the promotion happens, so nobody has to remember it.

Check yourself

Three questions

Which versions must every prediction from Kittiwake's twin carry to be auditable?

The building changes (a retrofit is a new configuration), the model is refitted, and the data has gaps handled by a rule. Without all three, "which model, of which building, on which data, said this?" has no answer.

Who should own the surprises (the innovations and the band coverage)?

The filter absorbs surprises into the state, so tracking still looks fine (0.258 C overall with the unlogged retrofit, constructed). Only someone reading the innovations sees floor 4's shift of z 11.44, and only someone with authority can stop the model acting on it.

When may Kittiwake's twin move from advice to action with a person approving?

With the unlogged retrofit the building covers 92.1 percent, inside the range, while floor 4 covers 69.0 percent and is 63.1 percent off on energy (constructed). A building-level gate would promote the wrong model.

Before session 9

Homework

  1. In the widget, switch the retrofit between logged and never logged. Write down which rows change verdict and which number does not change, and say in one sentence what that means for a version check.
  2. Extend gate.py to read a list of floor coverages and an innovation flag per floor, and refuse if any one floor fails. Run it on a toy card with one floor at 69.0 percent.
  3. For a twin or model you know, name the owner of each link of the loop, and the owner of the surprises. If a link has no name, write down who would find out first when it breaks.
  4. Write the demotion rule for Kittiwake: what flags a floor, which tier it drops to, and what it must pass to climb back.
